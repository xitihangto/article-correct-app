# 多文件 / 大文件上传方案调研

> 用途：新 app（一次上传 25 张图 → 生成一个 docx）开工前的技术底稿。  
> 与「高三英语作文批改」现有功能无关，只是把今天讨论过的内容整理成可查的文字。  
> 结论基于机制分析和一次响应头实测，**上传耗时本身没有实测过**，文件末尾列了待测项。

---

## 0. 一句话结论

现在把文件交给网页的方式是「base64 分片 + 逐片注入 JS」，**慢的不是上传，是把文件塞进 JS 环境**。  
25 张图大概要 700 次进程间往返；换成让网页自己去 `fetch` 本地文件，可以降到 25 次。

---

## 1. 现状：base64 分片方案

### 1.1 流程

```
磁盘文件
  → Swift 读成 Data
  → base64 编码（体积 +33%）
  → 切成 96000 字符一片
  → 逐片 evaluateJavaScript：window.__wbF[i] += '这一片'
  → 全部传完，调一次 commitFiles：
      atob 解码 → Uint8Array → new File() → DataTransfer → input.files
  → 网页当作正常附件收下
```

### 1.2 为什么慢

| 原因       | 说明                                                     |
| -------- | ------------------------------------------------------ |
| 进程间往返次数多 | 每 96000 字符一次 `evaluateJavaScript`，一次就是一次跨进程调用 + 字符串序列化 |
| 体积膨胀 33% | base64 把每 3 字节编码成 4 个字符                                |
| 数据被搬两遍   | Swift 侧编码一次，JS 侧 `atob` 解码一次                           |
| 拼接开销     | 每片都是 `字符串 += 字符串`，累积到几十 MB 时每次拼接都可能产生大临时副本             |

### 1.3 量级估算（**未实测，仅估算**）

以 25 张、每张 2MB 的图为例：

- 原始 50MB → base64 后约 67MB 字符
- 67MB ÷ 96000 ≈ **700 片**
- 若每片耗时 80ms，总计约 **56 秒**
- 现有作文版传 4 个文件要几秒到十几秒，量级对得上

### 1.4 为什么当初选它

**慢，但完全可控。** 不依赖 CSP、不依赖跨源策略、不碰私有 API、每一步都能打日志。  
当时只有 4 个文件、几 MB，够用。

## 2. 方案对比

|                | 现状 base64 | 加大分片     | scheme handler + fetch |
| -------------- | --------- | -------- | ---------------------- |
| 改动量            | —         | 改一个常量    | 新增约 100 行 + JS 改造      |
| 预估耗时（25 张 2MB） | ~56 秒     | ~10-15 秒 | 可能十几秒                  |
| 风险             | 无         | 低        | 中（未实测）                 |
| 主线程卡顿          | 小         | 明显（单次更长） | 很小                     |
| 失败时调试信息        | 每步都有日志    | 同左       | 只有 "Failed to fetch"   |
| 依赖             | 无         | 无        | 自定义 scheme + CORS 头    |

## 3. 方案 A：加大分片（零风险退路）

把 96000 改成一个更大的值，比如 512K 字符。

**好处**

- 700 次往返 → 约 130 次
- 拼接次数同步减少，规避 `+=` 的 O(n²) 风险（这一点上大分片是帮忙的）

**副作用**

1. **主线程卡顿变明显**。`evaluateJavaScript` 最终在主线程做字符串序列化和 JS 解析，512K 一片可能卡 150ms 以上。窗口虽然隐形，但主界面进度播报会一顿一顿。
2. **失败代价变粗**。一片失败要重传 512K（不过现在没有重试逻辑，失败直接抛，暂时不成立）。
3. **进度粒度变粗**。影响很小，因为进度是按「第几个文件」报的，不按片。

**硬上限**：不要往几 MB 一片走。字符串太大时 WebKit 内部要整段转 NSString 跨进程传输，内存峰值和解析时间会突然跳起来，有被拒绝或崩掉的风险。512K 是相对安全的位置。

**真正的价值**：如果测下来发现大分片也还是慢，说明瓶颈不在分片大小，而在「必须走 JS 字符串」这件事本身 —— 那就该上方案 B 了。

## 4. 方案 B：WKURLSchemeHandler + fetch（推荐优先验证）

### 4.1 原理

给 WKWebView 注册一个自定义 URL 前缀（比如 `essayfile://`），App 自己实现「收到这个请求就从磁盘读文件返回」。然后页面里的 JS 直接：

```js
const r = await fetch('essayfile:///path/to/1.jpg');
const blob = await r.blob();
const f = new File([blob], '1.jpg', { type: 'image/jpeg' });
// 后面 DataTransfer → input.files 完全不变
```

### 4.2 为什么快

**数据不经过 JS 字符串。** 由 WebKit 的 native 层直接把文件内容交给 Web 进程，等于找回了「手动拖拽上传」的零拷贝优势。

25 次 fetch 代替 700 次同步注入，而且 fetch 是异步的，可以并发。

### 4.3 风险逐条

**① CSP —— 已实测排除**

DeepSeek 首页的响应头里，CSP 只有这一条：

```
content-security-policy: frame-ancestors 'none'
```

只有 `frame-ancestors`，**没有 `default-src`、没有 `connect-src`**。  
也就是说它只禁止被别的页面 iframe 嵌套，**对 fetch 的源完全不作限制**。

（这条是 2026-10-28 用 curl 实测的，UA 用 Safari 的。）

**② CORS —— 可控**

页面 origin 是 `https://chat.deepseek.com`，我们的 scheme 是 `essayfile://`，属于跨源。  
但 `WKURLSchemeHandler` 的响应头是我们自己写的，加一行 `Access-Control-Allow-Origin: *` 即可。  
而且是简单 GET 请求，不会触发 preflight。

**③ `x-content-type-options: nosniff` —— 要注意**

DeepSeek 的响应头里有 `x-content-type-options: nosniff`，意思是禁止浏览器猜类型。  
所以我们自己返回的 `Content-Type` 必须给准（`image/jpeg`、`image/png`、`application/pdf` 等），给错了会被拒。

**④ 未实测**

`WKURLSchemeHandler` 的设计目的就是让自定义 scheme 像 http 一样被 fetch，理论上通。  
但 WebKit 具体版本有没有细节坑，只有跑一次才知道。**这是唯一剩下的未知数。**

### 4.4 验证方法（约 20-30 分钟）

1. 在现有 App 里注册一个 scheme handler，随便指向一张本地图
2. 在页面控制台 `fetch` 一下，看能不能拿到 blob
3. 能拿到 → 看 `blob.size` 对不对、`new File()` 后能不能塞进 `input.files`
4. 全部通过 → 这条路可用；任何一步失败 → 退回方案 A

## 5. 为什么不能「模拟用户手动上传 / 粘贴」

看着最像真人操作，实际上做不到：

| 想法                              | 为什么不行                                                                                                       |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 模拟点击 `<input type=file>` 再自动选文件 | 点击后弹的是系统文件选择框（NSOpenPanel），那是独立进程的 UI，程序没法替用户在框里点「打开」。能做的只有私有 API（`_setFileInputFiles`）或辅助功能驱动，前者不稳、后者要用户授权 |
| 往剪贴板塞图再发 ⌘V                     | 会污染用户剪贴板；而且会触发网页自己的粘贴处理逻辑。这个方案在作文版上试过并放弃                                                                    |
| 模拟拖拽文件到页面                       | 拖拽是跨进程的 drag session，NSEvent 注入模拟不出来                                                                        |

所以「把 File 对象交给页面」这一步无法绕过，区别只在于数据怎么进去。

## 6. 建议的验证顺序

1. **先做方案 B 的可行性验证**（20-30 分钟）。CSP 这条最大的风险已经排除，值得一试。
2. 通了 → 用它。25 张图应该十几秒级。
3. 不通 → 做方案 A 的分片大小对照测试：96K / 256K / 512K / 1M，同一批图各跑一次记录总耗时，取拐点。
4. 两条都试完再决定，别凭感觉选。

## 附：几个术语

- **base64**：把二进制数据编码成纯文本的方式，每 3 字节变 4 个字符，体积涨 33%。
- **IPC / 进程间通信**：这里指 App 主进程和网页渲染进程之间的数据传递，每次调用都有固定开销。
- **WKURLSchemeHandler**：WebKit 提供的接口，让 App 自己接管一种 URL 前缀，像提供文件服务一样。
- **CSP（Content-Security-Policy）**：网页通过响应头声明「允许加载哪些资源」，能限制脚本、图片、fetch 的来源。
- **CORS**：跨源资源共享。A 源的页面去请求 B 源的资源时，B 源必须明确允许。
- **nosniff**：禁止浏览器根据内容猜测文件类型，要求服务端给的 `Content-Type` 必须准确。
